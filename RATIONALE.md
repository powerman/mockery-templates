# Rationale

Why these templates exist and why [mockery](https://github.com/vektra/mockery) v3
is used as a generic interface-driven Go code generator
instead of dedicated generators like go-mockgen, gowrap or counterfeiter.
Decided in 2026-10.

## Context

Stateful fakes were generated by go-mockgen
(the `unknwon` fork of `derision-test/go-mockgen`).
Go 1.27 removed `GODEBUG=gotypesalias=0`,
so an alias like `type Ctx = context.Context` now always has type `*types.Alias`,
and go-mockgen panicked with `Unexpected type *types.Alias: expected *types.Named`
for any package containing an alias of an interface type.
Upstream `derision-test/go-mockgen` v2.1.1 does not even build with Go 1.27
(old `golang.org/x/tools`).
Both repositories show little activity (59 and 1 stars, last pushes in 2025),
so the generator effectively has no maintainer.

The fix itself was trivial (skip aliases),
and a patched fork (`github.com/powerman/go-mockgen/v2`) is used as a stop-gap.
The question was what to use long-term, for ~50 projects kept uniform by a copier template:
fakes are used only in a few of them today, but are expected to replace mocks in more tests.

## Requirements

In priority order:

1. **Readable, concise tests.**
   The fake API must support a per-method hook queue on top of a default hook,
   call history, and a constructor delegating all methods to a real implementation
   (e.g. an in-memory store with a single method overridden to return an error).
2. **The usage style must not provoke mistakes.**
   No interface names or paths duplicated in directives.
   No hand-written per-interface glue that silently goes stale:
   a hand-written `NewFakeXFrom` misses methods added later,
   and a "returns" setter used instead of a queue silently turns
   a one-shot override into a permanent one.
3. **The generator is maintained by someone else.**
4. **Any output placement:** the interface's own package,
   another package (public test-helper packages with their own package doc,
   used by other packages and modules),
   external and internal `_test` packages, another Go module.
5. **Self-contained generated code** (stdlib only):
   test helpers must not leak dependencies into binaries or into the module graph of users.
6. **Simple invocation:** no multi-line mise tasks or wrapper scripts.
7. Generated files are named `*.*.go`.

## Decision

- **mockery v3 is used as a generic interface-driven code generator.**
  It owns the hard part: loading packages, types, imports, generics, aliases.
  Templates own only the shape of the generated code.
  mockery v3 was redesigned around templates
  with the stated goal of letting template developers maintain and distribute their own,
  and the data passed to templates (package `github.com/vektra/mockery/v3/template`)
  is documented as backward compatible.
- **The first template, `gomockgen`, is API-compatible with go-mockgen v2.1.1.**
  Existing tests migrate without changes,
  the go-mockgen README keeps serving as documentation of the semantics,
  and no new API has to be designed.
  Extensions, if ever needed, must be additive.
- **Interfaces are selected in `.mockery.yml` only.**
  `//mockery:` directives are not used:
  mixing config and directives means two ways to do one thing,
  a type would need several directives,
  and misspelled directive keys are silently ignored.
- **Templates are copied into projects** (planned via the copier template)
  rather than fetched over `https://` on every generation:
  generation works offline and template updates show up as ordinary diffs.
- **The same machinery replaced gowrap** in `go-monolith-example`
  (its in-process in-adapter template):
  as a stress test of mockery as a general generator,
  and to keep a single template syntax per project.

## Alternatives considered

- **counterfeiter.**
  `*.*.go` names require duplicating the directory and interface name in directives;
  a sed hack was needed to keep the generated header from becoming the package doc;
  no hook queue with a default hook;
  the author deliberately keeps the tool inflexible.
- **mockery's built-in `matryer` template plus a small add-on template.**
  Tried on two projects: the config became complex,
  queue-based test cases degraded into call-counting closures,
  and one-shot overrides silently became permanent.
- **gowrap as the template engine.**
  Viable: full Sprig, one `//go:generate` line per type.
  But it cannot generate into an external `_test` package
  (the package clause comes from the destination directory),
  produces one file per interface with `-i`/`-o`/`-t` repeated for each,
  and has a single maintainer.
- **Maintaining the go-mockgen fork long-term.**
  Means owning a parser-based generator — exactly the situation this decision avoids.
- **minimock, gomock.** Mocks with expectations, not fakes.

## Consequences and known risks

- **The templates are maintained here.**
  Mitigated by fixtures, behavior tests and CI in this repository.
  Generated code is committed and self-contained,
  so even an abandoned template breaks nothing at run time.
- **This path is little-trodden.**
  No third-party mockery template repositories were found (2026-10).
  Edge cases are less tested than the core:
  the built-in `matryer` template generates a non-compiling `var _ Gen[comparable]`
  for a generic interface constrained by `comparable`.
- **mockery aborts when any loaded package fails to type-check**
  (`internal/parse.go`, no opt-out), unlike gowrap and go-mockgen.
  An output placed in the interface's own package therefore breaks regeneration
  as soon as the interface changes.
  Projects delete all mockery outputs before running mockery
  (found by their `// Code generated by mockery` header);
  this also removes outputs orphaned by config changes.
- **Ordering with `go generate` is not automatic.**
  mockery runs first, because `//go:generate` tools may consume its outputs
  (e.g. mockgen on a generated interface); rerun generation when a step needs a later one.
- **Stale config fails loudly:** an unknown package or interface is an error.
- **Template functions are fewer than Sprig** (e.g. no `regexReplaceAll`),
  which is mostly compensated by type-aware methods of the template data.
- **Team adoption.**
  The go-mockgen API is niche and no more familiar to a team than a custom one,
  but compatibility keeps existing documentation valid and avoids API design churn.
